# Issue #2931 - Nightly Rust fails on `uncommon_codepoints` in zerocopy derives

## Goal

Make `torrust-tracker-udp-protocol` compile again with nightly Rust under the repository's
`-D warnings`, so the nightly CI jobs pass, without hiding the lint anywhere else in the
workspace.

## Background

The nightly jobs of CI (for example `Build on macos-latest (nightly)` in `OS Compatibility`) fail
with 17 errors `identifier contains an uncommon character: 'ẕ'` in
`packages/udp-protocol/src/announce.rs`, `scrape.rs` and the other files that derive zerocopy
traits. It was first seen on PR #2920, a docs-only PR (see the
[note on that PR](https://github.com/torrust/torrust-tracker/pull/2920#issuecomment-6972484078)).
The reported source lines are plain ASCII field names.

What happens, step by step:

1. The structs in `torrust-tracker-udp-protocol` derive `IntoBytes`, `FromBytes` and `Immutable`
   from `zerocopy` 0.8.63.
2. `zerocopy-derive` 0.8.63 (`src/derive/project.rs`, lines 154 and 172) generates one item named
   `ẕ<field>` (U+1E95, LATIN SMALL LETTER Z WITH LINE BELOW) per struct field, and gives that
   identifier the span of the user's field name. That is why the errors point at our code.
3. rust-lang/rust#165289 ("lexer: Update to Unicode 18", merged 2026-11-17) updated rustc's
   Unicode security data. U+1E95 is no longer an allowed identifier character, so the
   `uncommon_codepoints` lint (warn by default) now fires on every generated identifier.
4. The repository's global `rustflags` (`-D warnings`) turn those warnings into errors.

The first nightly with the change is rustup `nightly-2026-11-18`
(`rustc 1.102.0-nightly (59cbdee2e 2026-11-17)`); `nightly-2026-11-17` (`5df8c02af 2026-11-16`)
compiles cleanly. It is not specific to macOS and not an sccache artifact: it reproduces on Linux
(see `manual-verification-evidence.md`). It is an intended data change upstream, so later nightlies
will not undo it; it reaches stable Rust in a later release unless zerocopy changes its generated
names first.

Impact: every pull request and `develop` fail the nightly jobs. Stable builds and the tracker's
runtime behavior are not affected.

## Scope

### In Scope

- Add a crate-level `#![allow(uncommon_codepoints)]` to `packages/udp-protocol/src/lib.rs`, with
  a comment that explains the cause and links the upstream issue, and says to remove the allow
  once a zerocopy release no longer generates non-ASCII identifiers.

### Out of Scope

- Allowing the lint workspace-wide (in `.cargo/config.toml`) or in other crates: only this crate
  uses the zerocopy derives.
- Pinning the nightly toolchain in the workflows: it would touch five workflows to get the same
  effect, and it would need someone to remember to unpin it.
- Changing or downgrading the `zerocopy` dependency.
- Filing the upstream report on google/zerocopy (to be done separately with the maintainer's
  approval; this issue links it once it exists).

## Architectural Decisions

- Related ADRs: none.
- ADRs to create: None known.

A narrower item-level `#[allow(uncommon_codepoints)]` on each struct was tried and does not
silence the lint: rustc only honours this lint's level at crate level (rust-lang/rust#86824).

## Regression Test Strategy

The defect is a compiler lint on code generated by a third-party proc macro under a specific
toolchain, so no Rust unit or integration test can express it. The smallest maintained check that
fails for the defect and passes for the fix is the compile step itself on nightly, which CI already
runs in `OS Compatibility` and `Testing` on every push and pull request that changes non-Markdown
files (and in `Deployment` on release branches). No new test is added;
the red/green evidence is the `cargo check` run recorded in `manual-verification-evidence.md`.
