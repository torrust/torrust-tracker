# Issue #2280 - Generate V1 Schema and Verify Drift

**Parent EPIC:** #2264 - Refactor Semantic Link and Frontmatter Conventions

**Predecessor:** [#2266 - Implement the Rust Frontmatter Model and Initial Validator](../../closed/2266-2264-implement-rust-frontmatter-model-and-validator/ISSUE.md)

## Goal

Generate a tracked JSON Schema Draft 2020-12 projection of the canonical Rust v1 frontmatter
model and prevent drift between the generated artifact and its deterministic offline source.

## Background

Issue #2266 established the canonical Rust representation for the universal envelope, strict issue
and EPIC profiles, and frozen semantic-reference syntax. It intentionally split schema generation
into this independently reviewable follow-up. The generated schema helps editors, agents, and
non-Rust consumers discover field presence, primitive types, enums, nullability, list/mapping
shape, and approved reference patterns without becoming a second manually maintained contract.

The schema artifact will live at `docs/schemas/frontmatter-v1.schema.json`. Its source is the
`frontmatter-validator` crate; humans must never edit the generated artifact to change contract
semantics.

## Scope

### In Scope

- Add current compatible `schemars` support to the non-published `frontmatter-validator` crate.
- Derive or otherwise generate a Draft 2020-12 schema from the canonical Rust v1 types without
  maintaining a separate schema model.
- Track the generated artifact at `docs/schemas/frontmatter-v1.schema.json`.
- Provide documented offline regeneration and deterministic drift-verification commands using the
  workspace Rust toolchain only.
- Add focused tests proving generated schema identity and drift failure behavior.
- Document invariants that remain in Rust validation because JSON Schema cannot express them.

### Out of Scope

- CLI invocation, file discovery, `--staged`, whole-tree modes, or NDJSON diagnostics; #2281 owns
  those command-surface concerns.
- Pre-commit, CI, pre-push, nightly, release, or agent-policy integration.
- New frontmatter fields, semantic-link forms, or strict document profiles.
- Replacing Rust structural validation with JSON Schema validation.
- Selecting the final automation architecture owned by #2003.

## Architectural Decisions

- Schema source: canonical Rust v1 types in `frontmatter-validator`; no manually authored schema
  duplicate.
- Artifact: `docs/schemas/frontmatter-v1.schema.json` in JSON Schema Draft 2020-12.
- Generation: an offline Rust command or test-owned generator in the crate; its exact public form
  will follow existing repository command conventions discovered during T1.
- Drift: deterministic generated bytes are compared to the tracked artifact and produce a failing
  focused check when they differ.
- Boundary: YAML delimiter extraction, quoted-scalar requirements, cross-field invariants,
  ownership/path discovery, repository existence, and lifecycle/location rules remain Rust or
  command-layer concerns unless the generated schema can express them without a parallel model.
- Related ADRs: `docs/adrs/20260519000000_define_global_cli_output_contract.md`.
- ADRs to create: None expected; create one only for an enduring repository-wide schema ownership
  or generation decision not already approved by #2265 and #2266.

## Design and Ownership Review

The schema module owns projection from canonical v1 Rust types. A generator owns deterministic
serialization and the tracked artifact. A focused test or command owns byte-for-byte drift
comparison. The future #2281 command layer may consume the model but does not own generation.

No network access, child processes, asynchronous I/O, persistent resources, or reusable runtime
fixtures are required. Generated output is deterministic repository content, not a runtime cache.

## Risks and Trade-offs

- `schemars` cannot automatically represent YAML lexical requirements or every cross-field rule.
  Keep those checks in the Rust validator and make the boundary explicit.
- Deriving schema from structures that contain parser-only representation may expose implementation
  details. Use an existing canonical strict type or a narrow schema-facing view only when it does
  not duplicate contract semantics.
- Generated JSON formatting can create noisy diffs. Use deterministic serialization and an exact
  byte comparison rather than normalizing the tracked artifact at check time.
