# GitHub Security Scanner Findings Process

This process applies to the public GitHub Security tab findings generated by CodeQL or the
Code Quality checks (`code-scanning` and `quality` views), not to confidential disclosures or
private vulnerability reports handled by [docs/security/vulnerability-remediation.md](vulnerability-remediation.md).

## Purpose

The GitHub Security tab is a recurring source of findings, but it is not a single problem to
fix in one long-lived issue. Many reports are duplicates of the same underlying root cause,
expressed in multiple files or multiple workflow jobs. We therefore treat these results as a
periodic review backlog, not as an EPIC-driven implementation queue.

## AI Skill Architecture

Security work remains split across focused skills because the publication boundary and required
evidence differ by source:

- `triage-github-security-findings` handles public Code Scanning and Code Quality findings;
- `catalog-security-vulnerabilities` handles public CVE, dependency, and container warnings;
- `run-manual-docker-security-scan` runs and records the runtime-image scan;
- confidential reports follow `vulnerability-remediation.md` and must not enter a public skill
  workflow that creates issues or analysis records.

This document is the policy source of truth for GitHub Security tab triage. The corresponding
skill is the executable adapter: it supplies discovery terms, routes to the correct security
workflow, and provides a concise checklist. It should link to this document rather than duplicate
all policy detail.

Do not create one centralized "review and fix all security issues" skill. Such a skill would make
it too easy to publish confidential findings or apply container-CVE assumptions to source-code
alerts. Add or refine a focused skill only when a distinct repeatable workflow exists.

## Principles

1. **Cluster before fixing.** A single code pattern or root cause may appear in many files.
   Create one issue per root cause or remediation class, not one issue per file.
2. **Keep the backlog searchable.** Record the issue inventory in a durable public document so
   triage results are not lost when the scanner output changes.
3. **Do not treat a scanner finding as automatically exploitable.** Each result is reviewed for
   impact, risk, and real code path before a fix is assigned a severity or priority.
4. **Track non-affecting cases explicitly.** Some findings are valid but do not affect this
   project, or are already mitigated by existing controls. These are recorded as a known
   non-affecting / accepted result, not left implicit.
5. **Prefer small, reviewable issues over a giant cleanup.** If the same root cause spans many
   files and the remediation is not one tiny change, create separate issues for each affected
   subsystem or each distinct fix strategy.
6. **Prioritize by trust boundary.** Runtime and release-supply-chain findings have the highest
   potential priority. Ordinary CI is lower unless it can pivot into releases, credentials, or
   privileged shared infrastructure. Local development and test findings are normally lower still.

## Severity, Surface, and Priority

The scanner's severity and the repository's priority are different fields. For every cluster,
record:

- scanner severity and rule identifier;
- affected surface: `runtime`, `release-supply-chain`, `ci-build`, or `development-test`;
- reachability and required attacker control;
- privileges, credentials, artifacts, or environments exposed by a successful exploit;
- whether the weakness can pivot into a higher trust tier;
- maintainer-assigned repository priority and rationale.

Apply the priority model in [`README.md`](README.md):

- shipped application, runtime OS and libraries, runtime Cargo dependencies, and published
  production images belong to the highest trust tier;
- CD and release publishing also belong to the highest tier because malicious artifacts can reach
  downstream users;
- CI-only findings normally have medium priority but escalate when runners, caches, permissions,
  or secrets provide a release or credential pivot;
- test-only and local-development findings normally have lower priority unless they can compromise
  a maintainer or poison a committed or published artifact.

This repository does not operate the separate demo deployments. Those environments are assessed
in their owning repositories. This repository must still protect its published crates, container
images, and release credentials as production-impacting assets.

## Review Cadence

Review the public GitHub Security tab regularly, at minimum:

- once per release cycle;
- whenever a dependency or workflow change affects a previously-reviewed finding class;
- immediately after a high-risk or newly introduced scanning rule appears in the repository.

The review is a lightweight triage cycle. It is not required to fix every finding in the same
iteration; the goal is to identify the actual shared issues and route them into manageable work.

## Triage Workflow

1. **Refresh the list.** Pull the current Code Scanning and Code Quality results from the
   repository security tab.
2. **Group identical findings.** Cluster by the rule name, approximate root cause, and affected
   subsystem. For example, repeated workflow-permission findings belong together even when they
   appear in multiple YAML files.
3. **Classify each cluster.** Use one of the following labels for the triage record:
   - `affecting`: the issue is real and needs a concrete fix;
   - `hardening`: the issue is valid but the project already has a compensating control or the
     risk is low enough that a future hardening improvement should be tracked separately;
   - `non-affecting`: the finding does not apply to this project, or the rule is a false
     positive in the current code context;
   - `needs-investigation`: the issue looks real but requires a code-path review before a fix is
     assigned.
4. **Assign surface and priority.** Apply the trust-tier model, document any pivot into a higher
   tier, and assign repository priority independently of scanner severity.
5. **Create one issue per finding class.** The issue should describe the root cause, the scope,
   the affected files or workflows, and the acceptance criteria. Use the `Security` label and a
   priority appropriate to actual risk. Do not create a single umbrella issue for all results.
6. **Keep an inventory of resolved and non-affecting findings.** When a finding is triaged,
   recorded as accepted, or intentionally not fixed, document the outcome so it is not reopened
   from scratch later.
7. **Fix and re-run checks.** Each grouped issue should include the verification steps required to
   confirm the fix and a re-scan trigger after merge.
8. **Schedule the next review.** The scanner backlog is recurring; every re-scan runs the same
   clustering and inventory process again.

## Inventory Structure

Use `docs/security/analysis/github-security/` for the durable public record:

- `README.md` is the cluster and disposition ledger;
- `reviews/YYYY-MM-DD.md` records each review snapshot and its source-alert coverage.

Each source alert must resolve to exactly one cluster row in the dated review. The cluster ledger
links to the current issue, accepted disposition, or completed remediation. This separates the
stable decision history from GitHub's changing alert list.

## What to Record in Each Issue

Each issue should contain at least:

- the scanner rule name or weakness class;
- the affected repository area (workflow, configuration, Rust crate, script, test helper, etc.);
- the affected security surface and whether a pivot to a higher trust tier exists;
- whether the finding is truly affecting, non-affecting, or a hardening gap;
- the maintainer-assigned priority and why it differs from or agrees with scanner severity;
- the root-cause explanation and why the same warning appears in multiple places;
- the planned fix or accepted disposition;
- a link to the evidence or a short rationale for the accepted decision;
- the review date and the owner responsible for the next follow-up.

## Preferred Issue Granularity

The project should prefer these patterns:

- one issue for a repeated GitHub workflow permission pattern;
- one issue for a repeated file-handle lifecycle cleanup pattern;
- separate issues for different security domains when the remediation cannot be shared;
- no EPIC solely to track the entire security tab backlog.

A broad "fix all security findings" issue is discouraged because it mixes unrelated fixes and
makes it difficult to review, verify, and close the work.

## Non-Affecting Inventory

Some scanner findings legitimately turn out to be not applicable to this project, or they are
already mitigated by repository controls, architecture, or runtime configuration. These findings
must still be recorded so that maintainers can tell the difference between:

- a known accepted issue;
- a temporary false positive;
- a previously fixed weakness that has new evidence but no current risk;
- a genuine active vulnerability that remains unpatched.

Keep this inventory under `docs/security/analysis/github-security/` and reference the relevant
cluster from issue specifications and accepted dispositions.

## First Implementation

The first triage cycle should document the process itself and then perform a real review of the
current list. That work is tracked by issue #2493 and its repository specification in
[`docs/issues/open/2493-security-code-scanning-triage/ISSUE.md`](../issues/open/2493-security-code-scanning-triage/ISSUE.md).

The goal is a repeatable process, not a one-off cleanup list. Once the first scan has been
reviewed and clustered, future scans can reuse the same structure without re-opening the design
questions.
